# 02 — Keys & integrity model (the heart of Phase 1)

This is the crypto/data model the endpoint must implement. It reuses `DIOEncryptorV1`, `EncKeyEncryptorV2`,
and `KeyProvider` verbatim; the only new ideas are **what goes inside the group `data`** (a membership block +
the wrapped group private key) and a **chain link** between versions.

---

## 1. The three keys (recap, with where each lives)

```
user key (Uk)            per-user context identity keypair — the root the endpoint already manages
   │ ECIES-wraps
   ▼
group data key (Gk)      symmetric (32B), per group, versioned by keyId — encrypts the group's `data`
   │ AEAD-encrypts
   ▼
group `data` blob        contains publicMeta, privateMeta, the MEMBERSHIP BLOCK, and the wrapped GROUP PRIVKEY
                         └─ the group identity private key (GroupPriv) — the grantee secret
```

- **Group data key `Gk` (`keyId`)** — a normal `core::EncKey` (`{id, key}`), generated by
  `KeyProvider::generateKey()`, wrapped per-member via `EncKeyEncryptorV2` and submitted as `keys[]`
  (`KeyEntrySet[]`). Identical to how a thread distributes its key.
- **Group identity keypair `(GroupPub, GroupPriv)`** — generated by the endpoint at `createGroup`. `GroupPub`
  is sent in the clear as `groupPubKey` (stable; the grantee target). `GroupPriv` is **encrypted inside the
  group `data`** (under `Gk`), so any member who holds `Gk` obtains `GroupPriv` and can act as the group when
  reading group-granted containers.

> Why store `GroupPriv` inside `data` rather than a separate per-member wrap? Because every group member needs
> it, and they already all receive `Gk` (via `keys[]`). Encrypting `GroupPriv` once under `Gk` and committing
> it in the DIO is the minimal, integrity-protected distribution. (Phase 2 may revisit if epochs split this.)

---

## 2. What the group `data` contains (and is signed by the DIO)

`GroupDataEncryptorV5` (mirror of `ModuleDataEncryptorV5`) produces an encrypted-module structure whose
`DataIntegrityObject` (`ExpandedDataIntegrityObject`) commits **all** of the following via `fieldChecksums`:

| Field | Encrypted? | Purpose |
|-------|-----------|---------|
| `publicMeta` | signed, plaintext-readable | app metadata (as today) |
| `privateMeta` | signed + encrypted under `Gk` | app metadata (as today) |
| `groupPrivKey` | signed + encrypted under `Gk` | the group identity secret, delivered to members |
| `membership` | signed (plaintext or encrypted) | **`{ users[], managers[], groupPubKey, keyId, prevEntryHash }`** |

The DIO itself binds (unchanged core struct):
`creatorUserId, creatorPubKey, contextId, resourceId = groupId, timestamp, randomId, bridgeIdentity?`, plus
`structureVersion` and the `fieldChecksums` map. It is signed with the **author's** (`creatorPubKey`) private
key by `DIOEncryptorV1.signAndEncode`.

### The `membership` block (the new, group-specific part)
```
membership = {
  users:        UserId[]          // sorted; the authoritative member set for THIS version
  managers:     UserId[]          // sorted
  groupPubKey:  string            // binds the identity key this version uses
  keyId:        string            // binds the data-key version
  prevEntryHash: string | null    // G1 chain link: sha256 of the previous version's signed DIO blob; null at genesis
}
```
- Committing `users`/`managers` in the signed DIO is what lets the client **detect a bridge that lies about
  membership** (it cross-checks the DIO-committed set against the bridge-served `users`/`managers` — doc
  [03](./03-verification.md)).
- `prevEntryHash` is the **G1 chain link**. There is no `prevSignature` field on the bridge anymore; ordering
  integrity is entirely inside the DIO.

> Implementation note: the chain link can equivalently be carried as an optional `prevDioHash` field added to
> the DIO struct itself. Either works; keeping it inside the `membership` block avoids touching the shared
> core DIO type. Pick one and document the canonical bytes (it must hash deterministically — sort lists, fix
> field order — exactly as the existing DIO JSON does).

## 3. `createGroup` — what the endpoint builds

1. `Gk = KeyProvider.generateKey()` (data key, new `keyId`).
2. `(GroupPub, GroupPriv) = Crypto.generateKeyPair()` (group identity).
3. Build `membership = { users, managers, groupPubKey: GroupPub, keyId, prevEntryHash: null }` (genesis).
4. `GroupDataEncryptorV5.encrypt({ publicMeta, privateMeta, groupPrivKey: GroupPriv, membership }, Gk,
   authorPrivKey)` → encrypted `data` + signed DIO (author = caller).
5. `keys[] = KeyProvider`-wrap `Gk` to every member's user pubkey (`EncKeyEncryptorV2`, each entry DIO-signed,
   `EncKeyLocation = {contextId, resourceId: groupId-or-clientResourceId}`).
6. Submit `context.groupCreate { groupPubKey: GroupPub, users, managers, data, keyId, keys[] }`.

The bridge stores it; **nothing is verified server-side**.

## 4. `updateGroup` (full replace — incl. add/remove members)

1. `getGroup(groupId)` → current `Group` + history (and **verify** it, doc [03](./03-verification.md)) →
   obtain current head's signed-DIO hash `H` and current `Gk`/`GroupPriv`.
2. Decide the new member sets (`old ∪ added` or `old − removed`).
3. **On removal (or whenever you want the removed party excluded):** generate a fresh data key `Gk'`
   (`keyId'`) and a fresh group identity `(GroupPub', GroupPriv')`; otherwise you may reuse them.
4. `membership' = { users', managers', groupPubKey: GroupPub('), keyId: keyId('), prevEntryHash: H }`.
5. Encrypt `data'` (with `groupPrivKey = GroupPriv(')` and `membership'`) under `Gk(')`; sign DIO (author =
   caller).
6. `keys'[]` = wrap `Gk(')` to the **resulting** member set.
7. Submit `context.groupUpdate { id, groupPubKey: GroupPub('), users', managers', data', keyId('), keys'[],
   version, force:false }`. `version` = current `history.length` (optimistic concurrency; on
   `GROUP_VERSION_MISMATCH` re-`getGroup` and retry).

> Removal & forward secrecy (Phase 1 reality): server-enforced revocation is immediate (the bridge stops
> serving the removed member). To also make **new group content** unreadable to them, rotate `Gk`/`GroupPriv`
> as in step 3 and re-wrap only to remaining members. **Containers** the group grants into are a separate
> concern — see doc [04](./04-group-as-grantee.md) §4 (Phase 1 = eager full re-key; Phase 2 = lazy/epoch).

---

## 5. Distributing & recovering keys (reuse `KeyProvider`)

- **Distribute** (`keys[]`): `EncKeyEncryptorV2.encrypt(Gk-as-EncKeyV2ToEncrypt, recipientUserPub,
  authorPriv)` per member — same call sites threads use via `KeyProvider`. Each entry carries its own DIO +
  `secretHash` (HMAC binding to `EncKeyLocation`).
- **Recover** (read): `KeyProvider.getKeysAndVerify(...)` decrypts the caller's `Gk` entry, verifies its DIO +
  checksums + `secretHash`, and runs `UserVerifier` on the entry's author. Then the endpoint decrypts the
  group `data` with `Gk` → obtains `GroupPriv` + `membership` + metas.

No new key-distribution code — only the group `data` payload (membership block + `GroupPriv`) is new, and it
rides inside the existing module-data encryptor.

---

## 6. Signing primitive (must match what the bridge-free model assumes)

All signatures use the endpoint's existing **secp256k1 / SHA-256 / 65-byte compact ECDSA**
(`PrivateKey::signToCompactSignatureWithHash`, verified with `PublicKey::verifyCompactSignatureWithHash`, via
`ECCImpl`). The DIO JSON is serialized deterministically (the existing `dynamic::DataIntegrityObject` schema);
the `membership` block must serialize deterministically too (fixed field order, **sorted** `users`/`managers`)
so `prevEntryHash` and checksums are reproducible across clients.

---

## 7. Summary of what's new vs reused
- **New:** the `membership` block (member-set commitment + `prevEntryHash` chain link) and `groupPrivKey`
  inside the group `data`; `GroupDataEncryptorV5`/`GroupDataSchemaMapper` to (de)serialize them.
- **Reused unchanged:** DIO sign/verify, per-field checksums, ECIES key wrap (`EncKeyEncryptorV2`), key
  generation/distribution/verification (`KeyProvider`), the ECC primitive, `UserVerifier`.
